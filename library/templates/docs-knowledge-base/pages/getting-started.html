Getting started

From sign-up to your first alert in fifteen minutes.

This page walks through the four things every Beacon account needs: a monitor, somewhere to send alerts, a teammate, and a status page. Everything else in the docs assumes these exist.

1. Create your first monitor

From the dashboard, press New monitor, paste a URL and leave everything else on the defaults: a 30-second interval, checks from 14 regions, and a 60-second confirmation delay so a single slow response does not page anyone. Beacon runs the first check immediately and shows the response time by region.

For anything that is not a URL, pick a different type: TCP for a database port, DNS for a record you expect to stay put, SSL for certificate expiry, or heartbeat for a cron job. The Guides page covers each one.

2. Connect an alert channel

  • Settings, then Integrations, then Slack. Authorise the app and pick a channel. Incidents post there with a resolve button.
  • Add your mobile number under your profile for SMS and phone alerts. Beacon sends a code to confirm it.
  • Optionally add a webhook URL to push incidents into your own tooling. Payloads are signed; see the API reference.

3. Invite the team

Settings, then Team, then Invite. Members can acknowledge and resolve incidents; admins can edit monitors and billing. On the Team plan you can also build an on-call schedule so alerts go to whoever is up this week, with a backup after ten minutes.

Put at least two people on every escalation policy from day one. The monitor you forgot about is the one that fails while the only person on it is on a plane.

4. Publish a status page

  1. Status pages, then New page. Give it a name and pick which monitors it shows.
  2. It is live immediately at yourname.beacon.page. Add a CNAME to put it on your own domain; the certificate is automatic.
  3. Turn on subscriber emails so customers can get incident updates without asking your support team.

That is the whole setup. Beacon will email you a weekly summary of uptime and response times, and the dashboard shows the last 90 days per monitor.

Stuck? The chat bubble in the bottom-right of the app reaches an engineer, weekdays 6am to 6pm Pacific. Median first reply is nine minutes.

What happens during an incident

From a failed check to a resolved page.

  1. 1

    A check fails

    One region reports a timeout or a bad status code. Beacon immediately re-checks from two more regions.

  2. 2

    Confirmation

    If two regions agree and the confirmation delay has passed, an incident opens with the response body and timings attached.

  3. 3

    Escalation

    The policy fires: Slack first, then the on-call phone, then the backup after ten minutes if nobody acknowledges.

  4. 4

    Resolution

    Checks pass again, the incident closes itself, the status page updates and subscribers get the all-clear.

Before you go live

The launch checklist.

Twelve things we check on every new account during onboarding calls. Tick them off yourself in about twenty minutes.

Read the guides

Monitors

  • Every public hostname has an HTTP check
  • SSL expiry monitor on each certificate, 14-day warning
  • Keyword check on the login page, not just a 200
  • Heartbeat on nightly backups and queue workers
  • Confirmation delay of at least 60 seconds
  • Maintenance window set for your deploy slot

People and pages

  • Two or more people on every escalation policy
  • Phone numbers verified for everyone on call
  • Quiet hours set so non-critical monitors wait until morning
  • Status page on your own domain with a logo
  • Two-factor required for all members
  • A test incident run end to end, including the phone call
